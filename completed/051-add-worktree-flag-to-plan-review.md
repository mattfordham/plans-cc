# Add a worktree flag to plan-review

**ID:** 051
**Created:** 2026-10-13T00:00
**Type:** feature
**Status:** completed
**Completed:** 2026-10-14T00:00
**Branch:** feature/051-add-worktree-flag-to-plan-review

## What
Add a flag to review for a work tree review. So this would be, for example, working the way review currently works if something was executed in a work tree, but if the flag is passed to the review skill and the work tree doesn't exist, it would be created so that it could be reviewed and simultaneous to other in-progress work.

## Why
Adds value by enabling on-demand, at-review-time worktree isolation. Today a task can only be reviewed inside its own worktree (so review runs concurrently with other work) if it was executed with the `keep` keyword; a plain task occupies the shared main checkout and serializes review. This flag lets `/plan-review NNN worktree` create a worktree for an already-reviewable branch so it can be reviewed in isolation without re-running execution and without blocking other in-progress or in-review tasks.

## How Summary
Add a `worktree` keyword to `/plan-review` (mirroring plan-execute's `worktree` / `use worktree` / `with worktree` vocabulary). When the flag is present and the task has no live `**Worktree:**` field, a new step creates a worktree that checks out the task's **existing** branch (`git worktree add <path> <branch>`, no `-b` — unlike execute, which creates a fresh branch) and writes the `**Worktree:**` field back to the task file byte-identically to execute step 7e. Everything downstream (the step 3.5 worktree-vs-main decision, the step 3.6 concurrency guard, the step 5/6 in-worktree git commands) already handles a live `**Worktree:**` field, so creating the worktree and writing the field is the entire change — the task then reviews concurrently for free, and `/plan-complete` tears the worktree down exactly as it does a kept one.

## Assumptions

### Initial (from elaboration)
- [high] Use `worktree` / `use worktree` / `with worktree` as the keyword, reusing plan-execute's exact vocabulary rather than a `--worktree` flag. **Why:** review takes no description prose, so a bare keyword cannot collide with anything, and matching execute/spawn is the lowest-surprise choice (research recommended this).
- [low] A `worktree` flag on a task with no `**Branch:**` errors consistently with today's "Nothing to review" rather than creating a branch. **Why:** review is post-execution and presupposes committed work to review; creating a branch at review time is out of scope.
- [high] The created worktree checks out the task's **existing** branch (`git worktree add <path> <branch>`, no `-b`), NOT a fresh branch from the target. **Why:** the whole point is to review the committed work already on that branch; this is the one deliberate divergence from execute step 7e and the only semantic that makes sense.
- [low] A `worktree` flag on a task that already has a live `**Worktree:**` field is a silent no-op (review in the existing worktree). **Why:** the field already drives in-worktree review; re-creating would be wrong and erroring would be unfriendly.
- [low] Support full multi-repo parity (reference execute 7e multi-repo, write `**Repos:**`) rather than scoping v1 to single-repo. **Why:** the step 3.6 concurrency guard and `/plan-complete` teardown already handle multi-repo via `**Repos:**`, so leaving multi-repo unsupported would create an asymmetric footgun; referencing the existing multi-repo sequence keeps the surface small.
