# Rework /plan-spawn to not depend on sub-agents invoking the Skill tool

## What
Rework /plan-spawn to not depend on sub-agents invoking the Skill tool. The current skills/plan-spawn/SKILL.md fans out general-purpose Task agents and tells each to run `/plan-execute NNN yolo worktree` — but the Skill tool is only available in the main conversation, not in sub-agents, so spawned agents cannot actually invoke /plan-execute. Fix with Option 2: drop the wrapper-agent layer entirely. /plan-spawn itself should replicate plan-execute's orchestration — preflight, skip-mode elaboration, branch+worktree creation, status transitions, state files, PROGRESS.md updates, worktree finish/cleanup — and instead of spawning a wrapper agent that runs plan-execute, it spawns the real `plan-executor` agent directly per segment per task. The parallelism comes from running multiple tasks' segments concurrently (plan-executor is a real agent type, not a skill, so this works). Each task still ends in `review` status with low-confidence assumptions and deferred observations logged. Update skills/plan-spawn/SKILL.md to reflect this orchestration model; the frontmatter, argument parsing, confirm gate, and summary table mostly stay. Reference plan-execute's steps 7 (branch/worktree setup), 10 (segmentation), 11 (segment execution via plan-executor, state files, deferred observations in yolo/worktree mode), and 11e (worktree finish → review status).

## Why
Improves reliability by fixing a skill that cannot work as written. The Skill tool is only present in the main conversation; a spawned `general-purpose` agent told to "run `/plan-execute NNN yolo worktree`" has no Skill tool and will either fail or improvise plan-execute's 700-line behavior from prompt text — inconsistent and unverifiable. The real `plan-executor` agent IS a valid `subagent_type`, so the fix is to make plan-spawn itself the orchestrator (replicating plan-execute's loop) and delegate only implementation work to `plan-executor`, exactly as plan-execute already does. This makes `/plan-spawn` actually functional.

## Assumptions

### Initial (from elaboration)
- [high] plan-spawn invokes `/plan-elaborate NNN skip` directly from the main conversation rather than via a spawned agent. **Why:** plan-spawn runs in the main conversation where the Skill tool exists; the whole bug is that sub-agents lack the Skill tool. plan-execute's own auto-elaborate path (step 3 / step 7a) also invokes elaboration inline, not via a wrapper agent.
- [high] Implementation work is delegated to `subagent_type: "plan-executor"` with `model: "opus"`, using plan-execute step 11c's segment execution prompt template. **Why:** This is exactly what plan-execute step 11b does; plan-executor is a real agent type (`agents/plan-executor.md`), so it works from a sub-agent context. Reusing the same template keeps plan-spawn and plan-execute consistent.
- [high] Each task still ends in `review` status with deferred observations + low-confidence assumptions logged. **Why:** Explicit requirement in the task description, and matches plan-execute step 11e (worktree finish always sets `review`) and step 11b.6 (worktree/yolo mode defers observations).
- [low] Interleaving model: plan-spawn runs "rounds" — round N spawns segment N of every task that still has one, in a single message, awaits all, then sequentially reconciles each task's own state file. **Why:** The research confirmed per-task state files / branches / worktrees are isolated and safe to parallelize, while shared files (`config.json`, `PROGRESS.md`, `.plans/` commits) must be serialized. A round-based interleave is the simplest model that parallelizes across tasks while keeping each task's segments sequential (segment N+1 depends on segment N's state). An alternative — fully independent per-task pipelines — would need a different concurrency primitive; rounds fit the single-message-multi-Task-call contract cleanly.
- [low] Git operations that touch the shared repo `.git` (branch creation, `git worktree add`, `git worktree remove`) are performed by plan-spawn itself, serialized across tasks, NOT inside the parallel `plan-executor` spawns. **Why:** The plan-executor agents work *inside* their own worktrees (isolated working trees), but `git worktree add/remove` mutate the shared `.git` and could race if interleaved. Serializing the setup/teardown in the main conversation while parallelizing only the in-worktree implementation work is the safe split. Could revisit if git proves to tolerate concurrent worktree ops, but serial setup is cheap.
- [low] The wrapper agent's structured `BRANCH:/STATUS:/ASSUMPTIONS:/DEFERRED_OBSERVATIONS:/COMMITS:/BLOCKERS:/NOTES:` return format is removed entirely; plan-spawn computes those summary-table values itself from the state files and git. **Why:** With no wrapper agent there's nothing to return that format. plan-spawn already has direct disk access to every task's state file and the git repo, so computing Assumptions/Deferred/Commits/Outcome directly is more reliable than parsing a sub-agent's prose. The `plan-executor` agents still return their normal per-segment structured response (Completed/Decisions/Deviations/Blockers/Test Status) which plan-spawn consumes per round.
- [low] Frontmatter is unchanged — `Task` stays in `allowed-tools` (now used to spawn `plan-executor` instead of `general-purpose`), and no new tools are needed. **Why:** plan-spawn already had `Task`, `Bash`, `Read`, `Write`, `Edit`, `Glob`, `Grep`, `AskUserQuestion` — the rework redistributes how they're used but doesn't introduce a new capability. Could add nothing; verified the existing set covers branch/worktree git ops (Bash), state/task file writes (Write/Edit), and agent spawns (Task).

### Discovered during execution
- [high] Step 6b creates the branch via `git worktree add .worktrees/NNN-slug -b [branch-name]` and explicitly does NOT also run a bare `git checkout -b`. **Why:** plan-execute step 7c+7e: when worktree mode is on, the worktree command itself creates the branch; running `git checkout -b` first would make `git worktree add -b` fail (branch already exists). Spawn always implies worktree mode, so the worktree path is the only path.
- [high] Test-suite detection and CONTEXT.md read are placed in step 3 (Preflight) rather than a new dedicated step. **Why:** The segment prompt explicitly said to fold them into the rewritten step 3; keeping them there avoids renumbering steps 4-8, which segment 2 still needs to find at known numbers.
- [low] The rewritten step 6 instructs the orchestrator to hold each task's segment plan "in memory" and also reflect it in the state file's `## Segments` section. **Why:** plan-execute keeps segment ranges in the state file; mirroring that keeps resumability/consistency, but the live execution loop (next segment) reads from memory. Stated both so the handoff to the next step is unambiguous — could be simplified later if the loop is redefined to read purely from the state file.
- [low] Step 6 omits the multi-repo worktree path entirely (only single-repo `git worktree add .worktrees/NNN-slug` is documented). **Why:** The segment prompt referenced only plan-execute step 7e's single-repo command sequence and the task's How section describes single-repo commands; multi-repo spawn was not in scope for this rework. May need a follow-up if spawn should support multi-repo projects.
- [high] Final `## Steps` numbering settled on 1-9: 1-6 untouched, 7 = interleaved segment-execution loop, 8 = worktree-finish + post-spawn reconciliation (folded into one step), 9 = summary table. **Why:** The segment prompt offered either a 9-step or 10-step grouping; folding worktree-finish and reconciliation into one step 8 reads cleaner because both are sequential per-task post-execution cleanup with shared "computed from disk" framing, and it keeps the cross-references shorter.
- [high] The blocked-task summary row shows Status `in-progress` (not `review`). **Why:** Step 8a explicitly leaves a blocked task at `in-progress` since it is not ready for review; the pre-existing summary-table example already showed `in-progress` for the blocked row, so the reconciliation logic was written to match it rather than the reverse.
- [low] The malformed-output edge case detects failure from the agent response *combined with* on-disk state (segment not advanced, checkboxes not checked), rather than from the response alone. **Why:** A `plan-executor` can return a well-formed-looking response but not actually complete work; cross-checking disk state is more reliable than trusting prose. Could be simplified to response-only parsing if that proves sufficient in practice.
- [low] Step 7 documents no `AskUserQuestion` blocker gate (unlike plan-execute step 11b.7) — a blocker just stops one task and the batch continues. **Why:** Spawn is always autonomous/yolo, so there is no interactive user present to answer a "stop all vs. skip" prompt; per-task stop with batch continuation is the autonomous-mode analog. Matches the task's How step 4 ("stop spawning further segments for THAT task only").

## Notes
Follows up on task #009 (added /plan-spawn). The flaw: spawned sub-agents don't have the Skill tool, so they can't invoke /plan-execute. Option 2 chosen by user: plan-spawn becomes a parallel orchestrator over the real plan-executor agent, replicating plan-execute's orchestration itself.

Key research finding (concurrency): per-task artifacts (state files, task files, branches, worktrees) are isolated and safe to parallelize; shared artifacts (`.plans/config.json`, `PROGRESS.md`, `.plans/` git commits) must be read-once-up-front / written-once-post-spawn.
