# Bug-Aware Elaboration: Stated Root-Cause Hypothesis for Bug Tasks

**ID:** 032

**Status:** completed
**Completed:** 2026-08-21T15:49
**Branch:** feature/032-bug-aware-elaboration-diagnosis

## What
Make `/plan-elaborate` produce a **stated, reviewable root-cause hypothesis** for `bug` tasks,
instead of smuggling an unstated theory into the `## How` steps.

**The problem.** Today no step in the elaboration pipeline owns hypothesis formation:

| Step | Runs on | What it produces |
|---|---|---|
| 8 — research | `models.research` | Six *feature-shaped* answers: files to modify, current patterns, suggested approach, reusable code, warnings, open questions |
| 9 — process findings | main session | Pure plumbing: "Relevant Files" → scope, "Suggested Approach" → How steps |
| 9.5 — deep drafting | `models.reasoning` | Why / How Summary / How / Verification / Impact Scope |
| 10-13 | main session | Simplicity assessment, Path A/B/C gates, validation, Impact Scope |

Step 8's prompt never asks *why is this broken* — its closest field is "Current Implementation",
which is descriptive, not causal. Because the agent is told to find files a fix would touch, it
reasons backward from "what would a fix change" rather than forward from "what produces this
symptom." Step 9.5's return contract has no slot for a cause. So for a bug task, the root-cause
theory forms **implicitly** and lands encoded inside a How step:

```
- [ ] Step 1: Re-fetch the CSRF token in the retry path at src/auth/session.ts:142
```

That step *encodes* a causal theory without ever stating it, showing its evidence, or flagging its
confidence. If the theory is wrong you discover it during execution, and the reasoning that produced
it was never written down to be checked. **An unstated hypothesis cannot be reviewed** — that is the
defect, and it is independent of which model runs it.

**The deliverable.** Four changes, all building on completed task #031 (the `models` role map and the
`deep` keyword — the plumbing already exists and works):

1. **A conditional diagnostic research prompt for `type: bug`** at step 8, replacing the
   feature-shaped "files to modify / suggested approach" questions with diagnostic ones: how to
   reproduce, trace the symptom to its origin, and rank candidate causes by evidence. Non-bug tasks
   keep today's prompt verbatim.
2. **A `## Diagnosis` section** added to the step 9.5 reasoning-agent return contract, emitted
   **only** for bug tasks and positioned **before `## How`**. Carries ranked candidate causes, the
   evidence for each, explicit confidence levels, and a "to confirm" line.
3. **`bug` added to the step 9.5 auto-trigger criteria**, so bug tasks escalate to
   `models.reasoning` without the user having to type `deep`. Bug tasks are precisely the ones where
   diagnosis-before-plan pays off.
4. **`/plan-show` renders the `## Diagnosis` section**, following the existing `## How Summary`
   precedent (rendered when present, omitted when empty or still a placeholder).

**Load-bearing constraint: a diagnosis is a hypothesis, not a finding.** The section must carry
explicit confidence levels and a "to confirm" line, or it will read as established fact and work will
proceed against a confident-sounding guess. The existing `👁` observation-step machinery is the
natural mechanism — the confirm step should become a real, tagged How step so execution pauses for
the user to verify the cause before the fix is built on top of it.

Illustrative shape of the target section:

```markdown
## Diagnosis
**Most likely:** `session.refresh()` drops the CSRF token when the tab is backgrounded —
`src/auth/session.ts:88` clears `_token` on visibilitychange but the retry path at `:142`
never re-fetches it.
**Evidence:** only reproduces after backgrounding; the 403 body matches the token-missing branch.
**Confidence:** high

**Alternative:** Safari ITP evicting the cookie. **Confidence:** low — would affect fresh loads
too, and it does not.

**To confirm:** log `_token` at `:142` before the retry.
```

## Why
Delivers on a promise the project already makes but does not keep. `README.md:63` states that
elaboration performs "root cause analysis for bugs," and `plan-capture` tells every user capturing a
bug that "elaboration helps identify root cause vs symptoms and prevents fix-revert cycles"
(`skills/plan-capture/SKILL.md:181-183`). Neither is true today: the research prompt asks only
feature-shaped questions, so the causal theory forms implicitly inside a How step where it cannot be
reviewed, challenged, or checked against evidence. Making the hypothesis explicit is what turns
"prevents fix-revert cycles" from a claim into a mechanism.

## How Summary
Introduce a `## Diagnosis` section for `bug`-type tasks, generated by a new path-independent
`### Diagnosis Generation` rules block modelled directly on the existing `### How Summary Generation`
block — so Paths A, B, and C all honor it inline and the reasoning sub-agent (step 9.5) merely points
at the same rules rather than owning them. Feed it by making the step-8 research prompt conditional on
task type: bug tasks get diagnostic questions (reproduce, trace, rank causes by evidence) with a
*minimal* field rename, preserving the four return-field names that steps 9 and 10 plumb by name. Add
`bug` as a third sibling trigger clause on step 9.5 only, deliberately not touching step 10's Path A/B
routing. Render the section in `/plan-show` and document it in `CLAUDE.md`, following the How Summary
precedent at every touchpoint.

**Five design decisions resolved interactively during elaboration (2026-08-21):**

1. **Diagnosis is path-independent, not 9.5-only.** Research found the task as captured had a hole:
   step 9.5 requires `models.reasoning`, which `/plan-init` deliberately never seeds and this repo
   lacks — so in a default project bug tasks would get the new diagnostic research with nowhere to
   put the answer, reproducing the exact defect one layer up. Fixed by making
   `### Diagnosis Generation` a named rules block that Paths A/B/C honor inline, with 9.5 merely
   pointing at it. The reasoning model becomes a quality upgrade, not a prerequisite.
2. **Minimal field rename in the bug research prompt.** Steps 9 and 10 consume the research return
   format *by field name*, so renaming breaks scope detection and How drafting silently. Keep
   `Relevant Files`, `Reusable Existing Code`, `Approach Warnings`, `Open Questions`; swap only
   `Current Implementation` → `Symptom Trace` and `Suggested Approach` → `Candidate Causes`; re-map
   those two explicitly in step 9.
3. **No placeholder seeding in `plan-capture`.** Elaboration inserts the section when it writes,
   mirroring `## Impact Scope`. Avoids a dead placeholder on every feature task and a first-of-its-kind
   conditional in the capture template, and keeps the four other task-writing skills consistent by
   doing nothing.
4. **Confidence vocabulary is `high|medium|low`** — deliberately three-valued and deliberately NOT
   reusing the two-valued `[high]`/`[low]` assumption-bullet vocabulary, which would mix diagnoses
   into `plan-retrospect`'s assumption-cluster mining signal.
5. **A disproved hypothesis is annotated or struck through, never deleted.** One line in the rules
   block. `plan-cleanup:150` uses a confidently-worded disproved hypothesis as its worked example of
   a real hazard.

**Rejected: adding `bug` to step 10's NOT-simple list.** It would force every bug — including
one-line typo fixes — onto Path B's four-gate interactive flow, and would inflate the skip-mode
assumption ledger, which propagates into `plan-review`'s low-confidence block and
`plan-retrospect`'s mining signal. The goal is escalation to `models.reasoning`, and 9.5's trigger is
exactly that lever; Path A/B routing is a separate question. `bug` goes in 9.5's trigger only, with an
explicit note so a future maintainer does not sync the lists.

**Rejected: a `models.diagnostic` role.** `CLAUDE.md:296-314` is an extended argument against growing
the role map, ending in the `segment_threshold` phantom-key cautionary tale. Reuse `reasoning`.

feature-shaped inputs and giving it no slot for a diagnosis.

**Why `deep` alone is insufficient** (three specific gaps, all addressed above):

  findings gathered by the wrong questions. This is the biggest gap and it is *upstream* of model
  choice.
- Step 9.5's return contract has no `## Diagnosis` slot, so analysis would be squeezed into `## Why`
  or dissolved into How steps — reproducing the exact problem this task exists to fix.
- `bug` is not among step 9.5's auto-trigger criteria (which reuse step 10's NOT-simple test:
  `refactor` type, open questions, or "investigate/figure out/explore/design/architecture" in the
  description). Bug tasks therefore never auto-escalate.
